characters as text. Before the fix, Left moved the caret in NSTextView but the

test covers Left, Down, forward Delete and F1, while retaining Unicode payloads.

## Capture and AX-read correction

The September 11 log actually named the 66×20 Claude utility surface `Window`;
the accompanying claim that it was unnamed was wrong. A nonempty-title filter
cannot exclude it and also rejects legitimate untitled windows. Removed that
filter and the fallback to an arbitrary process window. The one AX main window
is authoritative; capture uses the first layer-zero record with those exact
bounds. This is an ID lookup for that window, with no ranking or switching.
When no corresponding capture is available, stale image/controls are cleared.

Removed the speculative per-attribute fallback. The SDK's AXUIElement.h documents
that options=0 returns per-attribute errors/nulls without aborting the batch;
the previous continuation provided no reproduced bulk-read incompatibility.

Added `PROBE_UNTITLED=1` to the fixture, with its state in the visible event log.
Through the mirror its blank-titled window showed correct pixels and controls;
Same label in Left group reported `Clicked Left group`. Exiting the fixture
removed its controls from the mirror. Fresh Claude capture and its full
accessible composer/sidebar worked with batch reads alone. Seven tests and
both signed builds passed. The capture test uses the recorded utility bounds,
checks an empty title, and rejects a nonmatching window instead of guessing.

## Focus: the proxy is imposing foreground input

The user asked why the actual pointer moves into the target instead of staying
in the mirror, and whether Codex itself needs to steal focus. The proxy calls
`NSRunningApplication.activate`, writes AXFrontmost, raises the target, and
posts pointer/scroll events to the global HID tap. Keyboard forwarding also
activates the target before posting to its process. A secondary monitor does
not isolate those shared input resources.

This is **not a requirement of macOS Computer Use**. The current
[official documentation](https://learn.chatgpt.com/docs/computer-use#when-to-use-computer-use)
explicitly supports background tasks on macOS, and separately describes Windows
as foreground-only. Local `@oai/sky` macOS wrappers address operations to an app
through the native helper; this review did not recover that helper's complete
native dispatch implementation.

Live check, proxy stopped: Computer Use targeted MirrorTarget directly on the
secondary display. Clicking its draft and typing `focus probe` succeeded while
`NSWorkspace.frontmostApplication` stayed `com.openai.codex`. A 10 ms poll over
25 seconds reported no change of foreground app or pointer during that trial
(pointer 559.64453125, 1825.953125 in AppKit coordinates). A separate direct
coordinate click reached the pad and also left ChatGPT foreground; the pointer
had moved by a later observation, so that second trial does not independently
establish cursor immobility. The fixture draft was cleared. These observations
read foreground-app metadata; no Computer Use targeted ChatGPT directly.

Re-read the same three local implementations from the
[earlier comparison](computer-use-engines-and-chatgpt-wrapper.md):

| Implementation | Background approach in the inspected local source | Foreground limitation |
| --- | --- | --- |
| iFurySt/open-codex-computer-use | AX actions, process-directed input, optional SkyLight synthetic target focus and window-local click metadata. | Global pointer delivery is separate and opt-in; ordinary snapshot recovery can still activate. |
| trycua/cua native macOS driver | Process/window-directed mouse and keyboard, private SkyLight functions with public API fallback, synthetic focus without raising. | Separate desktop/global paths; some window-server drag operations use foreground delivery. |
| openclaw/Peekaboo | AX actions and targeted text/input by default; `BackgroundInputDriver` uses SkyLight process delivery with public fallback. | Explicit foreground mode for operations such as physical pointer moves, drags, and some shortcuts/dialog flows. |

These are source comparisons, not new live reliability tests of those engines.
Do not copy their ranking, fallback, or multi-window machinery into this project.
The next focused experiment should retain our one window and compare targeted
event delivery against the current global path, measuring both target outcomes
and effects on the foreground app/pointer. Background input has not been
implemented in the mirror yet. Live acceptance is paused at this checkpoint.
